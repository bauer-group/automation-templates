# 📦 Semantic Release — Repository Config Contract

What `.github/config/release/semantic-release.json` in a **consuming repository**
actually controls, and what it does not.

## Overview

`modules-semantic-release.yml` does not hand your config to semantic-release. The
[`semantic-release` composite action](../../.github/actions/semantic-release/action.yml)
**builds its own `.releaserc.json`** and copies a fixed set of values out of yours.
Anything it does not copy is silently ignored — the file is read, the run is green,
and the setting has no effect.

That is worth stating plainly because the failure mode is invisible. A setting that
is ignored looks exactly like a setting that is applied but did not matter.

## Why the action owns the config

Release notes are generated by the action's own `notes/notes.mjs` rather than
`@semantic-release/release-notes-generator`, wired in through
`@semantic-release/exec`'s `generateNotesCmd`. The action therefore has to control
the plugin array: it needs its notes seam present exactly once, and the plugin
**order** decides whether your `prepareCmd` runs before or after the release commit.

## The six reserved plugins

These are always provided by the action. Listing them in your config does not add a
second instance — the entry is filtered out of the extra-plugins merge:

| Plugin | Provided as |
|---|---|
| `@semantic-release/commit-analyzer` | with your `releaseRules`, if set |
| `@semantic-release/exec` | with the action's `generateNotesCmd` **plus your other hooks** |
| `@semantic-release/changelog` | with your `changelogFile` / `changelogTitle`, if set |
| `@semantic-release/git` | with your `assets` / `message`, if set |
| `@semantic-release/github` | with your options, if any |
| `@semantic-release/release-notes-generator` | **not provided at all** — see *Known gaps* |

## What is read from your config

Exactly this, and nothing else:

| Your config | Effect |
|---|---|
| `.tagFormat` | replaces the default tag format |
| `commit-analyzer` → `.releaseRules` | replaces the default release rules |
| `changelog` → `.changelogFile` | which file the changelog is written to |
| `changelog` → `.changelogTitle` | changelog preamble (an existing preamble is preserved) |
| `git` → `.assets` | **which files the release commit includes** |
| `git` → `.message` | the release commit message |
| `exec` → every hook except `generateNotesCmd` | merged into the reserved `exec` entry |
| `github` → all options | merged into the reserved `github` entry |
| any plugin outside the six reserved | appended before `@semantic-release/github` |

Everything else — `branches`, plugin ordering, and any plugin option not in this
table — is ignored. `branches` comes from the workflow input, not the file.

## Version stamping: `exec` + `git.assets`

The common case, and the one with two halves that must both be right:

```jsonc
{
  "plugins": [
    ["@semantic-release/exec", {
      // runs during `prepare`, ahead of changelog and git
      "prepareCmd": "sed -i -E 's/^version = \".*\"/version = \"${nextRelease.version}\"/' app/pyproject.toml"
    }],
    ["@semantic-release/git", {
      // a file the hook writes but this list omits is stamped and then NOT committed
      "assets": ["CHANGELOG.md", "app/pyproject.toml"]
    }]
  ]
}
```

`generateNotesCmd` is the one `exec` hook you cannot set — it is deleted from your
options before the merge, so the notes seam cannot be displaced by accident. Every
other hook (`verifyConditionsCmd`, `prepareCmd`, `publishCmd`, `successCmd`, …) is
yours.

Your `exec` entry is merged into the action's reserved one at its fixed position,
**ahead of `changelog` and `git`**. That placement is what makes `prepareCmd` useful:
behind `git`, the hook would run after the release commit and stamp files nothing
commits. It is asserted by
[`tests/merge-exec-hooks.test.sh`](../../.github/actions/semantic-release/tests/merge-exec-hooks.test.sh).

> **A non-zero exit from any `exec` hook aborts the release.** `@semantic-release/exec`
> treats it as an unexpected error. `sed -i` on a missing file exits 2 and stops the
> run; `sed` whose pattern simply does not match exits 0 and stamps nothing at all.
> If a silent no-op would be worse than a failed release, add your own check:
>
> ```jsonc
> "prepareCmd": "sed -i 's/^__version__ = .*/__version__ = \"${nextRelease.version}\"/' app.py && grep -q '^__version__ = \"${nextRelease.version}\"$' app.py"
> ```

## Known gaps

**`@semantic-release/release-notes-generator` is inert.** The action does not include
the plugin — `notes/notes.mjs` replaces it — and it is reserved, so it is also filtered
out of the extra-plugins merge. A `presetConfig` for it in your config is dead weight,
**including the section titles it appears to define**: those live in `notes.mjs`'s own
`TYPES` table, and a config asking for different ones does not get them.

This one is no longer silent. The action now emits a warning when it finds the plugin
in a repository config, so the entry can be deleted rather than trusted.

## History

`3adf5e08` added `@semantic-release/exec` to the reserved set so the notes generator
could not be registered twice, but enforced the reservation by dropping the consumer's
`exec` entry outright — taking `prepareCmd` with it. Releases stayed green, tags and
GitHub releases stayed correct, and only the version *inside* the artifacts stopped
advancing. It ran for four releases across three repositories before anyone noticed.
Fixed in #97; the regression is now covered by the test linked above.

Writing this page surfaced the same mistake on `@semantic-release/github`: reserved,
but with no extraction behind it, so every option a repository set was discarded. That
one left even less trace than the `exec` case — there was no key to notice missing,
only releases that kept commenting on issues a repository had asked them not to touch.
Its options are read now, and the test covers them.
